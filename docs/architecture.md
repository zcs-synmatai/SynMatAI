# 架构与目录约定

## 当前实现

apps/web 是唯一可运行应用；apps/api 只有接口规划；packages/contracts 是类型草案。
页面先加载 workflow/workbench.js，再加载 copilot/assets-and-todos.js、copilot/composer-actions.js。
后两者复用并扩展原型中的全局函数，迁移时不可直接改成异步加载或 ES 模块。
工作流包括三个并行材料节点、宏观构件配置、调度求解、结果分析；新增计算节点沿用现有原型能力。

## 逐步演进

1. 确定登录权限、数据存储、模型文件大小、求解器运行环境和 AI 服务要求，再确定框架与服务端技术栈。
2. 将 workbench.js 中的节点状态、依赖计算、图形渲染、配置表单拆开；保留既有行为作为迁移对照。
3. 将全局函数覆盖替换为明确的状态与事件接口；后续前端 API 客户端放 src/services/，可复用控件放 src/components/。
4. 对接后端后，将演示数据移入 src/mocks/，真实业务请求通过 services 层完成；求解进程不得运行在浏览器 UI 中。
5. 服务端业务按项目、工作流、资产、待办、任务调度、AI 会话分模块；真实求解器适配与应用 API 分离。
6. 服务端成熟后，再按需求添加 workers/、数据库迁移与部署目录，避免维护空目录或假实现。

## 开发规则

- 页面和功能改动只在当前项目中完成，outputs 的旧原型保留作参考。
- 新业务代码按功能归属放 features；跨功能共享前先确定接口，避免新增隐式全局依赖。
- 测试贴近对应功能；服务端集成测试随真实 API 添加。现有 scripts 测试验证开发服务行为。
- 领域对象和字段约定优先放 packages/contracts；该草案须和真实 API 一起确认。
- 环境密钥放本机环境变量或未提交的 .env；浏览器公开配置不包含密钥。
- 样式目前沿用 v4 七层加载链。新增样式优先在 workbench.css 中处理；逐步收敛后再拆分公共变量和组件样式。
